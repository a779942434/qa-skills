# 缺陷记录、报告与归档

## 缺陷记录格式

每个已确认缺陷使用以下字段：

```markdown
### BUG-编号：标题

- 严重程度：P0/P1/P2/P3/P4
- 环境：
- 前置条件：
- 操作步骤：
- 预期结果：
- 实际结果：
- 复现率：
- 证据：
- 需求引用：
- 备注：
```

> 判定原则（防误报，2026-09-03）：确认缺陷前须多信号交叉——页面提示 + 接口 + 数据变化 + 截图，避免把「校验拦截有提示」写成缺陷；关键项建议人工/用户抽核（详见 references/playwright-strategy.md 的「组件库防误读与多信号判定」）。

严重程度口径：

- `P0 致命`：安全/隐私泄露、重大数据损失、核心服务不可用。
- `P1 严重`：核心流程受阻，或产生明显错误业务数据。
- `P2 一般`：需求不符但有替代路径，影响有限。
- `P3 轻微`：文案、样式、体验类问题。
- `P4 建议`：可优化建议、非阻断性体验优化，不影响功能正确性。

## 快速报告模板

快速模式只输出这四块，避免生成过多文档拖慢执行：

```markdown
# 测试报告：功能名称

## 结论
- 测试时间：
- 环境：
- 范围：
- 结果：通过 X，失败 Y，阻塞 Z
- 执行率：已给判定用例数 / 总用例数（如 26/39，66%）；误报数（经用户/人工抽核发现并更正），用于暴露脚本脆弱与覆盖缺口
- 上线建议：

## 已测主链路
- 链路：
- 测试数据：
- 数据记录（产生/扣减）：本轮产生哪些单号、扣减哪些量（测试环境保留造数仍须留痕）

## 问题清单
- BUG-001：
- 待确认：
- 待人工复核：
- 环境观察：

## 本次未覆盖
- （显式列出未验证项：如导入、特定筛选、权限场景、数据受限项；避免含糊带过）

## 证据
- 截图：
- 导出文件：
- 核对 SQL/接口：
- 人工抽核：关键交互（重要弹出/toast/级联选择）已截图，建议人工/用户抽核一次（防自动化误报）
```

## 归档规则

1. 项目存在 `knowledge-base/` 时，优先归档到：
   - `test-plans/`
   - `test-cases/`
   - `bug-reports/`
   - `test-reports/`
2. 快速模式默认只生成 `test-reports/` 和 `bug-reports/`；
   除非用户要求，不单独生成完整测试计划和大用例表。
3. 文件名格式：`YYYY-MM-DD_功能名_类型.md`。
4. 缺陷清单命名 `YYYY-MM-DD_功能名_缺陷清单.md`，
   字段（环境/操作步骤/预期/实际/复现率/严重程度/需求引用）与 ones-create-linked-defect 兼容，
   可直接作为该技能的输入录入 ONES。
5. 缺陷现场截图与导出文件按功能归档（人员资质/排产数据等目录不同，勿混用），
   供 ONES 提缺陷时粘贴证据。
6. 最终回复只给结论、缺陷、路径和下一步建议，不粘贴长篇报告正文；报告含「执行率 / 误报率」统计与「数据记录（产生/扣减）」。
