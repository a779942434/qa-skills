# 制造类业务测试用例生成

把制造 / MES 类需求（PRD、流程图、补充规则、字段清单）转换为**八列用例表**（用例ID / 需求点 / 优先级 / 测试模块 / 测试点 / 前置条件 / 操作步骤 / 预期结果），并附需求点清单与覆盖矩阵：每条用例可追溯到需求原文，步骤给具体值、预期可判定。严格按需求原文生成，不脑补未提及逻辑；颗粒度支持「标准功能测试版 / 开发自测版」。

## 使用流程

1. 收集输入并按优先级排序：**补充规则 > 原 PRD > 流程图**；具体规则 > 通用规则；明确写死 > 推导逻辑。
2. 先「需求点化」：拆成编号需求点 R-01…（每条 = 一句可独立验收的条件/规则 + 原文引用 + 出处），作为全部用例的锚点。
3. 确认颗粒度 → 输出 Markdown 用例文档（需求点清单 + 用例表 + 覆盖矩阵）→ 完成四项收尾自查。

> 每步细则、书写规范、正反例 → `references/method.md`（生成时读，本文不重复）。
> 文档模板 → `references/template.md`；高频专项（多级拆分/数量守恒、派生字段、导入导出、造数配方、配置权限）→ `references/scenarios.md`（按需读）。

## 需求边界优先（强制）

通用检查清单只能作「候选检查」，不得直接升级为需求点、用例、缺陷或待确认项。

- 需求明确提到的：必须拆成需求点并生成用例。
- 需求未提到但执行时顺手发现的行为：只作「额外观察」，不得写成「需求未明确-需产品确认」。
- 需求未提到的通用场景（导入覆盖、部分成功、批量边界、并发、权限等）默认不测；要补充先取得用户或产品明确授权。
- 禁止把 `scenarios.md` / `test-scope.md` 等通用清单当成当前 PRD 的验收范围。

## 字段录入方式强制拆解

字段需求不能只写「支持新增/编辑/自动生成」。凡出现**手动输入、下拉单选/多选、日期选择、开关、自动带出、不填自动生成、全局唯一、重复校验**任一描述，必须把「控件类型 / 输入方式」与「数据行为」拆成**独立**需求点和用例，每条各自可判定。四个断言缺一不可：

1. **控件类型**：文本 / 下拉 / 级联 / 日期 / 开关 / 只读——不得用正确的数据结果掩盖错误的控件形态。
2. **输入方式**：能手动输入 / 只能选择 / 可多选 / 不可编辑——用真实键盘或组件标准操作验证。
3. **留空与默认**：必填拦截 / 使用默认值 / 按编码规则自动生成。
4. **唯一性与重复**：重复时是否拦截；拦截后列表与已存在数据是否不变。

> 反例：需求写「生产订单分单号手动输入、不填自动生成、全局唯一」，只出一条「可留空自动生成」。
> 正例：拆成「控件为文本输入」「可手动输入并保存」「留空自动生成」「重复值拦截」四条。

## 输入要求

支持：PRD（功能说明、字段明细、按钮规则、状态流转）、业务流程图（判断节点、分支走向、异常提示）、补充规则记录（聊天记录、需求变更、逻辑补丁，**优先级最高**）、字段清单（筛选/表格/弹窗字段的取值来源、编辑属性、校验规则）。

质量最低要求（缺失时索要，或标注「需求未明确」）：功能入口与操作主体、生效范围、核心判断的是/否分支、关键字段取值来源与默认值、操作后的数据变更规则（原单/新单、状态、数量）。

## 数据依赖与前置确认

- 用例文档开头给出**数据勘察清单**：逐条列出各用例前置所依赖的具体数据条件（如「存在剩余配料>0 的计划」）并标注当前是否现成。
- 前置条件引用**可复用造数配方**造出的状态描述（产品 / 工艺路线 / 地点组织 / 工序与报工等），不写繁琐推演。
- 满足不了的条件**显式标注**「数据受限未覆盖」，并在覆盖矩阵与报告「本次未覆盖」单列——不脑补、不硬测。
- 同时列出**需求未明确项**（报错文案、停留位置、口径等），执行前先向用户/产品确认；确认不了的标「需求未明确-需产品确认」，不编造预期。
- 与 web-blackbox-testing 的分工：本技能只做「用例层面的数据依赖与造数配方」，执行侧的数据勘察由黑盒测试落实，互指不重复。

## 输出结构

一个 Markdown 用例文档，四段式：

1. **用例说明**：覆盖范围、排除范围、依据来源
2. **需求点清单**：R-01… 编号 + 原文引用 + 出处（含「需求未明确」条目）
3. **用例表**：按五层模块分组的八列用例表
4. **覆盖矩阵**：需求点 ↔ 用例ID 双向清单，交付前逐项核销

## 避坑清单

1. **补充规则必置顶**：聊天记录、需求变更优先于原 PRD，先改写对应用例。
2. **判断节点不丢分支**：每个菱形对应正反两条用例，不能只测正常流。
3. **状态流转单独成组**：状态变更拎出来单独验证，避免混在功能用例里遗漏。
4. **不脑补未提功能**：需求没写的异常处理、边界逻辑一律不写。
5. **联动只测结果**：跨模块联动只测数据是否同步，不测对方模块内部逻辑。
6. **派生字段必用接口/DB 核对**：计算/汇总字段不能只看 UI，用接口/DB 验证公式与分支场景。
7. **配置/权限必测**：页签/按钮/数据权限、参数配置项属需求的一部分，不能省略。
8. **多规则叠加单独成组**：单节点正反分支覆盖不到「多规则同时命中」，需专门构造。
9. **字段录入四件套不可合并**：控件类型、输入方式、留空/默认、唯一性各自可判定。
