# 制造类业务测试用例生成

## 概览

把制造 / MES 类业务需求（PRD、流程图、补充规则、字段清单）转换为结构化六列表格测试用例。
严格按需求原文生成，不脑补未提及逻辑；支持「标准功能测试版」与「开发自测版」两种颗粒度。

## 使用流程

1. 收集输入并按优先级排序：补充规则 > 原 PRD > 流程图；具体规则 > 通用规则；明确写死 > 推导逻辑。
2. 按「七步生成法」拆解需求（见下）。
3. 确认颗粒度（标准功能测试版 / 开发自测版），输出 Markdown 用例文档。
4. 交付前完成三项收尾自查。

## 输入要求

支持的输入类型：

- PRD 需求文档：功能说明、字段明细、按钮规则、状态流转
- 业务流程图：判断节点、分支走向、异常提示
- 补充规则记录：聊天记录、需求变更、逻辑补丁（优先级最高）
- 字段清单：筛选区 / 表格区 / 弹窗字段的取值来源、编辑属性、校验规则

输入质量最低要求（信息缺失时向用户索要，或在该用例标注「需求未明确」）：

- 明确功能入口、操作主体、生效范围
- 明确核心判断逻辑的「是 / 否」分支走向
- 明确关键字段的取值来源、是否可编辑、默认值
- 明确操作后的数据变更规则（原单 / 新单、状态、数量）

## 七步生成法

### 第 1 步：提取 5 类核心要素

| 要素类型 | 提取内容 |
| --- | --- |
| 入口要素 | 按钮位置、显示条件、禁用条件、权限控制 |
| 校验要素 | 前置校验、提交校验、唯一性校验、必填校验 |
| 状态要素 | 初始状态、状态流转路径、状态联动影响 |
| 字段要素 | 取值来源、默认值、是否可编辑、显示格式 |
| 联动要素 | 跨表、跨模块、跨页面的数据同步规则 |

### 第 2 步：搭建模块骨架（五层功能 + 数据一致性 + 配置权限）

按「从外到内、从入口到结果，再到数据与权限」分层：

1. 入口校验层：按钮显示 / 禁用、权限控制、前置拦截
2. 基础交互层：弹窗打开 / 关闭、二次确认、字段默认值
3. 核心功能层：按功能模式拆分（按数量 / 百分比、手动 / AI、单 / 双面板）
4. 数据结果层：提交后原单变更、新单生成、字段取值、状态变更
5. 跨模块联动层：对其他模块的影响、跳转带参、批量操作
6. 数据一致性与派生字段层（重点）：所有**计算/派生字段**的公式，以及「有/无子级、有/无关联数据、负数、完全/部分/未拆分」等各分支场景各一条；需用**页面与接口/数据库核对**，不能只看 UI 显示
7. 配置与权限层（重点）：页签/菜单名称配置（如【订单类型及权限分配】）、角色权限控制（按钮/页签/数据可见性）、参数配置项

> 说明：第 6、7 层是 MES 类拆分/报表最容易出缺陷的地方（数据口径、链路守恒、规则冲突、导入导出、权限），**不能只停留在 UI 流程**；派生字段必须逐一给出公式并覆盖分支场景。

### 第 3 步：处理规则冲突与多规则叠加

- 补充规则 > 原 PRD > 流程图：聊天记录的逻辑补丁直接覆盖原需求描述
- 具体规则 > 通用规则：如「先具体产品后通用产品」的匹配优先级
- 明确写死 > 推导逻辑：只认需求原文，不脑补未提及逻辑
- **多规则叠加必须测**：专门构造「多条校验/限制同时命中的状态」各一条用例，验证哪个规则优先、是否按预期规则拦截（例如：一条记录既「未拆分」又「已下发」，删除时命中的是哪条限制；拆分后是否同时不可编辑/不可删除/不可再拆）。这类「规则冲突」靠单节点正反分支覆盖不到，容易漏（常见于需求未明确的部分，需标注「需产品确认」）。

### 第 4 步：流程图节点全覆盖

- 每个菱形判断节点拆「是 / 否」两条用例：否分支对应报错提示、拦截逻辑；是分支进入下一节点继续拆解
- 终点节点对应最终数据结果、成功提示

### 第 5 步：按六列表格写用例

一条用例只测一个测试点。列结构：

| 字段 | 填写规则 |
| --- | --- |
| 用例ID | `TC-模块缩写-序号`，序号三位递增，如 `TC-SP-001` |
| 测试模块 | 归属分层模块（入口校验 / 核心功能 / 数据变更等） |
| 测试点 | 一句话概括被测逻辑，精准到字段 / 按钮 / 规则 |
| 前置条件 | 可直接照着造数据的数据、状态、权限 |
| 操作步骤 | 1 / 2 / 3 步清晰描述动作，无冗余 |
| 预期结果 | 只写可验证的客观结果，无模糊表述 |

### 第 6 步：按受众调整颗粒度

- 标准功能测试版：每个判断节点正反分支各一条；每个字段规则一条；每个状态流转一条；每个联动影响一条
- 开发自测版：合并同类校验，突出核心分支；保留主流程、边界规则、数据变更结果；减少纯 UI 交互用例；前置条件直接给出数据配置方式

### 第 7 步：收尾自查

1. 需求全覆盖：所有功能点、判断节点、字段规则都有用例对应
2. 无超纲内容：所有预期结果都能在需求里找到依据，无自行扩展功能
3. 逻辑自洽：相同规则在不同用例中描述一致，无前后矛盾

## 输出结构

输出一个 Markdown 用例文档：用例说明（覆盖范围、排除范围、依据来源）+ 按五层模块分组的六列表格。

- 完整模板：见 [references/template.md](references/template.md)
- 高频场景拆解要点：见 [references/scenarios.md](references/scenarios.md)

## 专项场景与数据链路（拆单 / 排产 / 报表等高频）

以下场景在标准功能测/深度专项测中都应**单独成组**，不能只靠五层功能分支覆盖：

### 1. 数据链路与数量守恒（多级拆分/拆单必测）
- 多级拆分链（如 一级到二级到三级到四级）各级生成、父子 id 关联、编号规则
- **数量守恒**：每级子项数量之和 ≤ 父项数量；拆完剩余=0
- **删除回退**：删除子级后父级剩余可拆分/数量是否回补
- **撤销恢复**：撤销拆分后子级是否删除、父级是否恢复拆分前状态、状态是否透传

### 2. 派生字段逐一核对
- 每个计算字段给出公式 + 分支场景：有/无子级、有/无关联（如报工）、负数、部分/完全/未拆分
- 用**接口/数据库**与页面核对，不能只看 UI

### 3. 导入 / 导出 / 批量操作专项
- 导入：模板**必填标记**与需求核对、日期/金额**格式**、缺必填、非法值、重复、覆盖/去重、部分成功部分失败
- 导出：**所见即所得**（字段+数据+日期/数量显示格式）与页面一致
- 批量：批量编辑/批量拆分可编辑字段范围、数量之和约束、部分失败

### 4. 造数配方（前置条件基线）
- 在文档开头给出造数配方：准备哪些主数据（产品/工艺路线/地点组织/工序与报工），如何造出各状态基线数据（未拆分/部分拆分/完全拆分/已下发/有工序计划）供各用例直接复用
- 前置条件列一律用可复用配方造出的**具体状态**描述，不写繁琐推演

### 5. 配置与权限矩阵
- 页签/菜单名称配置项生效、默认值
- 角色权限：可见页签、可选按钮、数据范围

## 避坑清单

1. 补充规则必置顶：聊天记录、需求变更优先于原 PRD，先改写对应用例
2. 判断节点不丢分支：每个菱形必须对应正反两条用例，不能只测正常流
3. 状态流转单独成组：所有状态变更单独拎出来验证，避免混在功能用例里遗漏
4. 不脑补未提功能：需求没写的异常处理、边界逻辑一律不写
5. 联动只测结果：跨模块联动只测数据是否同步，不测对方模块内部逻辑
6. ID 命名统一：同一功能模块用例前缀一致，便于筛选维护
7. 派生字段必用接口/DB核对：计算/汇总字段（剩余可拆分、完工合格数、未完工数）不能只看 UI，用接口/DB 验证公式与分支场景
8. 配置/权限必测：页签/按钮/数据权限、参数配置项是需求的一部分，不能当背景省略
9. 造数先给配方：前置条件用可复用造数配方，否则用例难执行、造数重复
10. 多规则叠加/冲突单独成组：单节点正反分支覆盖不到「多规则同时命中」的场景，需专门构造
