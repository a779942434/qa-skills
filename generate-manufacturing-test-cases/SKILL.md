# 制造类业务测试用例生成

## 概览

把制造 / MES 类业务需求（PRD、流程图、补充规则、字段清单）转换为结构化八列用例表（用例ID / 需求点 / 优先级 / 测试模块 / 测试点 / 前置条件 / 操作步骤 / 预期结果），并附需求点清单与覆盖矩阵：每条用例可追溯到需求原文（不漏需求），步骤给具体值、预期可判定（AI 与人皆可照做）。
严格按需求原文生成，不脑补未提及逻辑；支持「标准功能测试版」与「开发自测版」两种颗粒度。

## 使用流程

1. 收集输入并按优先级排序：补充规则 > 原 PRD > 流程图；具体规则 > 通用规则；明确写死 > 推导逻辑。
2. 先「需求点化」：把需求拆成编号需求点 R-01…（每条 = 一句可独立验收的条件/规则，附原文引用与出处），作为全部用例的锚点；再按「七步生成法」拆解需求（见下）。
3. 确认颗粒度（标准功能测试版 / 开发自测版），输出 Markdown 用例文档（需求点清单 + 用例表 + 覆盖矩阵）。
4. 交付前完成四项收尾自查（见第 7 步，含覆盖矩阵双向核销与可执行性检查）。

## 输入要求

支持的输入类型：

- PRD 需求文档：功能说明、字段明细、按钮规则、状态流转
- 业务流程图：判断节点、分支走向、异常提示
- 补充规则记录：聊天记录、需求变更、逻辑补丁（优先级最高）
- 字段清单：筛选区 / 表格区 / 弹窗字段的取值来源、编辑属性、校验规则

输入质量最低要求（信息缺失时向用户索要，或在该用例标注「需求未明确」）：

- 明确功能入口、操作主体、生效范围
- 明确核心判断逻辑的「是 / 否」分支走向
- 明确关键字段的取值来源、是否可编辑、默认值
- 明确操作后的数据变更规则（原单 / 新单、状态、数量）

## 七步生成法

> **需求点化（下面所有步骤的前提）**：逐条通读全部输入（PRD、流程图节点、补充规则、字段明细），把「一句可独立验收的条件/规则」抽成一个需求点，编号 R-01、R-02…，并附**原文引用与出处**（如：PRD「字段说明-数量」行、补充规则#3、流程图判断节点 D2）。编号保持稳定，后文用例的需求点列、文末覆盖矩阵都引用它。判断标准：能同时判定「符合 / 不符合」，例如「分单数量：必填、>0、最多 5 位小数」。业务关键但需求未写明的条件也先编号列出，在用例中标注「需求未明确-需产品确认」，不编造预期。需求点化不是写用例，而是建立「需求 → 用例」双向追溯的锚点（防漏需求、防孤儿用例）。

### 第 1 步：提取 5 类核心要素

| 要素类型 | 提取内容 |
| --- | --- |
| 入口要素 | 按钮位置、显示条件、禁用条件、权限控制 |
| 校验要素 | 前置校验、提交校验、唯一性校验、必填校验 |
| 状态要素 | 初始状态、状态流转路径、状态联动影响 |
| 字段要素 | 取值来源、默认值、是否可编辑、显示格式 |
| 联动要素 | 跨表、跨模块、跨页面的数据同步规则 |

### 第 2 步：搭建模块骨架（五层功能 + 数据一致性 + 配置权限）

按「从外到内、从入口到结果，再到数据与权限」分层：

1. 入口校验层：按钮显示 / 禁用、权限控制、前置拦截
2. 基础交互层：弹窗打开 / 关闭、二次确认、字段默认值
3. 核心功能层：按功能模式拆分（按数量 / 百分比、手动 / AI、单 / 双面板）
4. 数据结果层：提交后原单变更、新单生成、字段取值、状态变更
5. 跨模块联动层：对其他模块的影响、跳转带参、批量操作
6. 数据一致性与派生字段层（重点）：所有**计算/派生字段**的公式，以及「有/无子级、有/无关联数据、负数、完全/部分/未拆分」等各分支场景各一条；需用**页面与接口/数据库核对**，不能只看 UI 显示
7. 配置与权限层（重点）：页签/菜单名称配置（如【订单类型及权限分配】）、角色权限控制（按钮/页签/数据可见性）、参数配置项

> 说明：第 6、7 层是 MES 类拆分/报表最容易出缺陷的地方（数据口径、链路守恒、规则冲突、导入导出、权限），**不能只停留在 UI 流程**；派生字段必须逐一给出公式并覆盖分支场景。

### 第 3 步：处理规则冲突与多规则叠加

- 补充规则 > 原 PRD > 流程图：聊天记录的逻辑补丁直接覆盖原需求描述
- 具体规则 > 通用规则：如「先具体产品后通用产品」的匹配优先级
- 明确写死 > 推导逻辑：只认需求原文，不脑补未提及逻辑
- **多规则叠加必须测**：专门构造「多条校验/限制同时命中的状态」各一条用例，验证哪个规则优先、是否按预期规则拦截（例如：一条记录既「未拆分」又「已下发」，删除时命中的是哪条限制；拆分后是否同时不可编辑/不可删除/不可再拆）。这类「规则冲突」靠单节点正反分支覆盖不到，容易漏（常见于需求未明确的部分，需标注「需产品确认」）。

### 第 4 步：流程图节点全覆盖

- 每个菱形判断节点拆「是 / 否」两条用例：否分支对应报错提示、拦截逻辑；是分支进入下一节点继续拆解
- 终点节点对应最终数据结果、成功提示

### 第 5 步：按八列用例表写用例

一条用例只测一个测试点，且必须锚定一个需求点（需求点化拆出的 R-xx）；没有需求点依据的用例一律不写（防脑补，也防无主孤儿用例）。列结构（标准功能测试版）：

| 字段 | 填写规则 |
| --- | --- |
| 用例ID | `TC-模块缩写-序号`，序号三位递增，如 `TC-SP-001` |
| 需求点 | 本用例验证的需求点编号 R-xx（可附原文缩略）；跨多需求点的组合用例列主需求点 |
| 优先级 | P0=核心成功流 / 金额·库存·权限 / 强校验与数据一致性（不通过即阻断）；P1=一般功能与规则；P2=次要交互与展示细节。宁少勿滥，一条用例一个优先级 |
| 测试模块 | 归属分层模块（入口校验 / 核心功能 / 数据变更等） |
| 测试点 | 一句话概括被测逻辑，精准到字段 / 按钮 / 规则 |
| 前置条件 | 可直接照着造数据的数据、状态、权限（引用造数配方），写不出具体状态就说明缺什么数据 |
| 操作步骤 | 1 / 2 / 3 步，遵循下方「可执行性书写规范」 |
| 预期结果 | 只写可验证的客观断言，遵循下方「断言书写规范」，无模糊表述 |

**可执行性书写规范（操作步骤）**
- 每个动作 = 「对什么对象、做什么操作、输入什么具体值 / 选什么选项」，例如「数量输入 0.000001 后点击保存」「选择页签「二级生产订单分单」」。禁止「核对 / 看看 / 按步骤执行 / 输入边界值 / 正常操作」等需要执行者二次演绎的动词。
- 同一条规则的多条边界 / 分支必须拆成多条用例并各自写死输入值，不允许一条用例里写「0 / 负数 / 超精度」让执行者自己挑。
- 涉及跳转写明入口路径或目标页签名；涉及造数，前置条件引用造数配方的具体状态（如「有一张已下发未拆分的一级分单」）。

**断言书写规范（预期结果，三段式取适用项）**
1. 页面结果：最终状态、toast / 提示文案（尽量引用需求原文，如提示含「分单数量必须大于 0」）；
2. 数据结果：字段操作前后变化（原值 X → 新值 Y），能写数值就写数值；
3. 核对点：明确到**页面 / 接口 / 数据库**哪一层验证（数据变更、计算 / 派生字段相关用例必给，如「列表无新增 + 无成功保存接口返回」）。
禁止「符合预期 / 正确 / 正常 / 按规则变更」等不可判表述；需求未写明的边界、上限、提示文案，标注「需求未明确-需产品确认」，不编预期。

示例（需求点 R-01「分单数量：必填、>0、最多 5 位小数」）：

| 用例ID | 需求点 | 优先级 | 测试模块 | 测试点 | 前置条件 | 操作步骤 | 预期结果 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| TC-SP-005 | R-01 | P0 | 核心功能 | 数量=0（下界恰等）拦截 | 新增弹窗已打开，其余必填已填 | 数量输入 0，点保存 | 拦截，提示含「必须大于 0」；列表无新增（无成功保存接口返回） |
| TC-SP-006 | R-01 | P0 | 核心功能 | 负数（无效等价类代表）拦截 | 新增弹窗已打开，其余必填已填 | 数量输入 -1，点保存 | 拦截并提示；列表无新增 |
| TC-SP-007 | R-01 | P0 | 核心功能 | 5 位小数最小正值可保存 | 新增弹窗已打开，其余必填已填 | 数量输入 0.00001，点保存 | 保存成功，列表显示 0.00001 |
| TC-SP-008 | R-01 | P0 | 核心功能 | 6 位小数（精度+1）拦截 | 新增弹窗已打开，其余必填已填 | 数量输入 0.000001，点保存 | 拦截，提示含「最多 5 位小数」；列表无新增 |
| TC-SP-009 | R-01 | P1 | 核心功能 | 数量上限 | 新增弹窗已打开 | 需求未规定上限 | 标注「需求未明确-需产品确认上限值与超限提示」，不写死预期 |

### 第 6 步：按受众调整颗粒度

- 标准功能测试版：每个判断节点正反分支各一条；每个字段规则一条；每个状态流转一条；每个联动影响一条
- 开发自测版：合并同类校验，突出核心分支；保留主流程、边界规则、数据变更结果；减少纯 UI 交互用例；前置条件直接给出数据配置方式；表格可去掉「测试模块」列（按模块分组已表达），但必须保留「需求点」「优先级」列

### 第 7 步：收尾自查（四项全部通过才算交付）

1. **需求全覆盖（按覆盖矩阵双向核销）**：文末给出覆盖矩阵——每个需求点 R-xx 至少 1 条正向 + 1 条反向用例（无法构造反向时注明理由，如纯展示项）；反向检查不存在找不到需求点依据的孤儿用例。矩阵出现空行 = 需求未覆盖，禁止交付。
2. **无超纲内容**：所有预期结果都能在需求里找到依据，无自行扩展功能；需求未写明的边界与提示一律标「需求未明确-需产品确认」，不编造。
3. **逻辑自洽**：相同规则在不同用例中描述一致，无前后矛盾。
4. **可执行可判定**：逐条核对——操作步骤都给了具体对象与输入值、预期结果符合第 5 步断言规范（页面结果 / 数据结果 / 核对点）、前置条件能引用造数配方造出；任何一条做不到即为未完成，返回重写。

## 输出结构

输出一个 Markdown 用例文档，四段式：

1. 用例说明：覆盖范围、排除范围、依据来源
2. 需求点清单：R-01… 编号 + 原文引用 + 出处（含「需求未明确」条目）
3. 用例表：按五层模块分组的八列用例表（用例ID / 需求点 / 优先级 / 测试模块 / 测试点 / 前置条件 / 操作步骤 / 预期结果）
4. 覆盖矩阵：需求点 ↔ 用例ID 双向清单，交付前按第 7 步逐项核销

- 完整模板：见 [references/template.md](references/template.md)
- 高频场景拆解要点：见 [references/scenarios.md](references/scenarios.md)

## 专项场景与数据链路（拆单 / 排产 / 报表等高频）

以下场景在标准功能测/深度专项测中都应**单独成组**，不能只靠五层功能分支覆盖：

### 1. 数据链路与数量守恒（多级拆分/拆单必测）
- 多级拆分链（如 一级到二级到三级到四级）各级生成、父子 id 关联、编号规则
- **数量守恒**：每级子项数量之和 ≤ 父项数量；拆完剩余=0
- **删除回退**：删除子级后父级剩余可拆分/数量是否回补
- **撤销恢复**：撤销拆分后子级是否删除、父级是否恢复拆分前状态、状态是否透传

### 2. 派生字段逐一核对
- 每个计算字段给出公式 + 分支场景：有/无子级、有/无关联（如报工）、负数、部分/完全/未拆分
- 用**接口/数据库**与页面核对，不能只看 UI

### 3. 导入 / 导出 / 批量操作专项
- 导入：模板**必填标记**与需求核对、日期/金额**格式**、缺必填、非法值、重复、覆盖/去重、部分成功部分失败
- 导出：**所见即所得**（字段+数据+日期/数量显示格式）与页面一致
- 批量：批量编辑/批量拆分可编辑字段范围、数量之和约束、部分失败

### 4. 造数配方（前置条件基线）
- 在文档开头给出造数配方：准备哪些主数据（产品/工艺路线/地点组织/工序与报工），如何造出各状态基线数据（未拆分/部分拆分/完全拆分/已下发/有工序计划）供各用例直接复用
- 前置条件列一律用可复用配方造出的**具体状态**描述，不写繁琐推演

### 5. 配置与权限矩阵
- 页签/菜单名称配置项生效、默认值
- 角色权限：可见页签、可选按钮、数据范围

## 避坑清单

1. 补充规则必置顶：聊天记录、需求变更优先于原 PRD，先改写对应用例
2. 判断节点不丢分支：每个菱形必须对应正反两条用例，不能只测正常流
3. 状态流转单独成组：所有状态变更单独拎出来验证，避免混在功能用例里遗漏
4. 不脑补未提功能：需求没写的异常处理、边界逻辑一律不写
5. 联动只测结果：跨模块联动只测数据是否同步，不测对方模块内部逻辑
6. ID 命名统一：同一功能模块用例前缀一致，便于筛选维护
7. 派生字段必用接口/DB核对：计算/汇总字段（剩余可拆分、完工合格数、未完工数）不能只看 UI，用接口/DB 验证公式与分支场景
8. 配置/权限必测：页签/按钮/数据权限、参数配置项是需求的一部分，不能当背景省略
9. 造数先给配方：前置条件用可复用造数配方，否则用例难执行、造数重复
10. 多规则叠加/冲突单独成组：单节点正反分支覆盖不到「多规则同时命中」的场景，需专门构造
