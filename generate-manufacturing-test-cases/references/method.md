# 七步生成法（用例生成细则）

> 由 `generate-manufacturing-test-cases/SKILL.md` 抽出，**生成用例时读**。
> 字段录入四件套（控件类型 / 输入方式 / 留空默认 / 唯一性）以 SKILL.md 为准，本文不重复。

> **边界规则**：通用清单不是需求点。只有需求原文或用户明确授权的内容才允许编号为 R-xx 并生成验收用例；
> 需求未提到的覆盖、去重、部分成功、并发等场景不写成「需产品确认」，应在排除范围说明「需求未定义」。

## 需求点化（所有步骤的前提）

逐条通读全部输入（PRD、流程图节点、补充规则、字段明细），把「一句可独立验收的条件/规则」抽成需求点，
编号 R-01、R-02…，附**原文引用与出处**（如 PRD「字段说明-数量」行、补充规则#3、流程图节点 D2）。
编号保持稳定，后文用例的需求点列与覆盖矩阵都引用它。

判断标准：能同时判定「符合 / 不符合」，例如「分单数量：必填、>0、最多 5 位小数」。
业务关键但需求未写明的条件也先编号列出，在用例句标注「需求未明确-需产品确认」，不编造预期。
需求点化不是写用例，而是建立「需求 → 用例」双向追溯锚点（防漏需求、防孤儿用例）。

## 第 1 步：提取 5 类核心要素

| 要素 | 提取内容 |
| --- | --- |
| 入口 | 按钮位置、显示条件、禁用条件、权限控制 |
| 校验 | 前置校验、提交校验、唯一性校验、必填校验 |
| 状态 | 初始状态、流转路径、状态联动影响 |
| 字段 | 取值来源、控件类型、输入方式、默认值、是否可编辑、显示格式 |
| 联动 | 跨表、跨模块、跨页面的数据同步规则 |

## 第 2 步：搭建模块骨架（五层 + 数据一致性 + 配置权限）

1. 入口校验层：按钮显示/禁用、权限控制、前置拦截
2. 基础交互层：弹窗开关、二次确认、字段默认值
3. 核心功能层：按功能模式拆分（按数量/百分比、手动/AI、单/双面板）
4. 数据结果层：提交后原单变更、新单生成、字段取值、状态变更
5. 跨模块联动层：对其他模块的影响、跳转带参、批量操作
6. **数据一致性与派生字段层**：所有计算/派生字段的公式，以及「有/无子级、有/无关联数据、负数、完全/部分/未拆分」等分支各一条；必须用页面 + 接口/DB 核对，不能只看 UI
7. **配置与权限层**：页签/菜单名称配置、角色权限（按钮/页签/数据可见性）、参数配置项

> 第 6、7 层是 MES 类拆分/报表最容易出缺陷处（数据口径、链路守恒、规则冲突、导入导出、权限），不能只停留 UI 流程。

## 第 3 步：处理规则冲突与多规则叠加

- 补充规则 > 原 PRD > 流程图（聊天记录的逻辑补丁直接覆盖原需求描述）
- 具体规则 > 通用规则（如「先具体产品后通用产品」的匹配优先级）
- 明确写死 > 推导逻辑（只认需求原文）

**多规则叠加必须测**：专门构造「多条校验/限制同时命中」各一条用例，验证哪个规则优先、是否按预期拦截
（例：一条记录既「未拆分」又「已下发」，删除时命中哪条限制；拆分后是否同时不可编辑/删除/再拆）。
这类规则冲突靠单节点正反分支覆盖不到，容易漏；需求未明确处标「需产品确认」。

## 第 4 步：流程图节点全覆盖

每个菱形判断节点拆「是/否」两条用例：否分支对应报错提示与拦截逻辑，是分支进入下一节点继续拆解；终点节点对应最终数据结果与成功提示。

## 第 5 步：按八列用例表写用例

一条用例只测一个测试点，且必须锚定一个需求点（R-xx）；没有需求点依据的用例一律不写（防脑补、防孤儿用例）。

| 列 | 写法要求 |
| --- | --- |
| 用例ID | 模块前缀统一（如 TC-SP-001），便于筛选维护 |
| 需求点 | 引用 R-xx，一条用例对应一个 |
| 优先级 | P0 主链路/强校验 → P1 边界/异常 → P2 展示/次要 |
| 测试模块 | 归属分层模块（入口校验 / 核心功能 / 数据变更等） |
| 测试点 | 一句话概括被测逻辑，精准到字段/按钮/规则 |
| 前置条件 | 可直接照着造数据的状态与权限（引用造数配方）；数据不足标「数据受限未覆盖」并注明缺什么 |
| 操作步骤 | 1/2/3 步，见下方可执行性规范 |
| 预期结果 | 只写可验证的客观断言，见下方断言规范 |

**可执行性规范（操作步骤）**
- 每个动作 = 「对什么对象、做什么操作、输入什么具体值/选什么选项」，如「数量输入 0.000001 后点保存」。
  禁止「核对 / 看看 / 按步骤执行 / 输入边界值 / 正常操作」等需二次演绎的动词。
- 同一规则的多条边界/分支必须拆成多条用例并各自写死输入值，不允许写「0 / 负数 / 超精度」让执行者自己挑。
- 涉及跳转写明入口路径或目标页签名；涉及造数引用造数配方的具体状态。

**断言规范（预期结果，三段式取适用项）**
1. 页面结果：最终状态、toast/提示文案（尽量引用需求原文，如含「分单数量必须大于 0」）；
2. 数据结果：字段操作前后变化（原值 X → 新值 Y），能写数值就写数值；
3. 核对点：明确到**页面/接口/数据库**哪一层验证（数据变更与派生字段用例必给）。

禁止「符合预期 / 正确 / 正常 / 按规则变更」等不可判表述；需求未写明的边界、上限、提示文案标「需求未明确-需产品确认」，不编预期。

示例（R-01「分单数量：必填、>0、最多 5 位小数」）：

| 用例ID | 需求点 | 优先级 | 测试模块 | 测试点 | 前置条件 | 操作步骤 | 预期结果 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| TC-SP-005 | R-01 | P0 | 核心功能 | 数量=0 拦截 | 新增弹窗已开，其余必填已填 | 数量输入 0，点保存 | 拦截，提示含「必须大于 0」；列表无新增（无成功保存接口返回） |
| TC-SP-008 | R-01 | P0 | 核心功能 | 6 位小数拦截 | 同上 | 数量输入 0.000001，点保存 | 拦截，提示含「最多 5 位小数」；列表无新增 |
| TC-SP-009 | R-01 | P1 | 核心功能 | 数量上限 | 新增弹窗已开 | 需求未规定上限 | 标「需求未明确-需产品确认上限值与超限提示」，不写死预期 |

## 第 6 步：按受众调整颗粒度

- **标准功能测试版**：每个判断节点正反分支各一条；每个字段规则一条；每个状态流转一条；每个联动影响一条。
- **开发自测版**：合并同类校验、突出核心分支；保留主流程/边界规则/数据变更结果；减少纯 UI 交互用例；前置条件直接给数据配置方式；可去掉「测试模块」列（按模块分组已表达），但必须保留「需求点」「优先级」。

## 第 7 步：收尾自查（五项全部通过才算交付）

1. **需求全覆盖**：覆盖矩阵双向核销——每个 R-xx 至少 1 条正向 + 1 条反向（无法构造反向时注明理由，如纯展示项）；反向检查无孤儿用例。矩阵出现空行 = 未覆盖，禁止交付。
2. **无超纲**：所有预期都能在需求里找到依据，无自行扩展功能。
3. **逻辑自洽**：相同规则在不同用例中描述一致，无前后矛盾。
4. **可执行可判定**：逐条核对操作步骤有具体对象与输入值、预期符合断言规范、前置能按造数配方造出；任何一条达不到即返回重写。
5. **数据可执行性**：前置所需数据都能按「数据勘察清单/造数配方」造出；造不出的标「数据受限未覆盖」并在矩阵/报告单列，不得硬测或留空。
